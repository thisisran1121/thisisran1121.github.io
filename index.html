  • 정합성 검증 — 건수 비교, MD5 체크섬, 동일 조건 쿼리의 양쪽 결과 교차 검증 절차 수립.

Key Achievements & Troubleshooting

문제 발생 → 분석 → 해결 → 결과 순으로 정리했습니다.

Oracle · Memory

HugePages 확보 실패로 인한 ORA-27106 인스턴스 기동 실패

Issue문제 발생

SGA를 HugePages에 고정하기 위해 use_large_pages=ONLY로 설정한 뒤, 필요한 HugePages가 확보되지 않아 ORA-27106: system pages not available to allocate memory로 인스턴스 기동이 실패했습니다.

Analysis분석

ONLY는 HugePages가 부족하면 일반 페이지로 fallback하지 않고 기동을 실패시키는 설정입니다(성능 저하 상태로 조용히 운영되는 것을 막기 위한 의도). 원인을 추적한 결과, 시스템 운영 중 누적된 메모리 단편화가 연속된 2MB 페이지 확보를 방해하고 있었습니다.

Solution해결

서비스 복구를 위한 완화 조치와 근본 원인 해소를 분리해 진행했습니다.

SQL> create pfile from spfile;      -- use_large_pages=TRUE로 완화 후 우선 기동
# sync; echo 3 > /proc/sys/vm/drop_caches   -- OS 캐시 정리로 단편화 해소
SQL> shutdown immediate; startup;   -- spfile(ONLY) 기반 재기동
Result결과

show parameter use_large = ONLY, HugePages_Total이 설정값(2,400, Oracle Doc ID 401749.1 스크립트 산출)과 일치함을 확인. HugePages는 계산값을 넣는 것으로 끝나지 않으며, 장애 시에는 "즉시 복구"와 "근본 해소"를 구분해 접근해야 한다는 운영 원칙을 체득했습니다.

PostgreSQL → Oracle · Migration

공식 전환 도구가 없는 역방향 이관 — 메타데이터 기반 파이프라인 직접 설계

Issue문제 발생

Oracle → PostgreSQL은 ora2pg를 사용할 수 있었지만, 반대 방향은 공식 전환 도구가 제한적이어서 multi_family_sales · single_family_sales (합계 1,710,788건)의 테이블 구조와 데이터를 옮길 방법을 새로 설계해야 했습니다.

Analysis분석

컬럼 구조는 SQL 표준 information_schema에서 얻을 수 있지만, 코멘트(pg_description)와 인덱스 정의(pg_class · pg_index · pg_attribute 등)는 PostgreSQL 전용 시스템 카탈로그를 참조해야 한다는 점을 확인했습니다.

Solution해결
  • information_schema.columns를 CASE로 분기해 Oracle 타입으로 매핑하고 string_agg로 CREATE TABLE 조립. 정의되지 않은 예외 타입은 ELSE VARCHAR2(4000)으로 폴백해 이관이 중단되지 않게 처리.
  • 같은 패턴으로 COMMENT · PK · UK · INDEX DDL 6종을 추출해 단일 스크립트로 결합. PK 인덱스는 USING INDEX TABLESPACE TS_SINDX로 데이터와 I/O 분리.
  • COPY TO로 CSV 추출 → md5sum 생성 → scp 전송 → 수신측 md5sum -c 검증 → SQL*Loader direct=true 적재 (rows=10000, bindsize/readsize 10MB, exit code 로깅).
Result결과

두 테이블 모두 MD5 OK, SQL*Loader exit code 0, Oracle 적재 건수가 PostgreSQL 원본(1,208,997 / 501,791건)과 정확히 일치. 도구가 없는 상황에서도 데이터 딕셔너리를 근거로 해결책을 설계할 수 있음을 확인했습니다.

PostgreSQL → Oracle · Data Type

timestamp → DATE 파싱 실패와 boolean 대응 타입 부재

Issue문제 발생

PostgreSQL의 timestamp 컬럼을 CSV로 추출해 Oracle DATE로 적재할 때 포맷이 맞지 않아 파싱이 실패했습니다. 또한 PostgreSQL의 boolean은 Oracle에 동등한 타입이 없었습니다.

Analysis분석

CSV는 텍스트이므로 날짜는 양쪽이 합의한 고정 포맷 문자열로 주고받아야 하며, 타입이 없는 값은 의미가 보존되는 다른 타입으로 명시적으로 매핑해야 한다고 판단했습니다.

Solution해결
-- 추출(PostgreSQL): copy_to.sql 자동 생성 시 타입별 변환
TO_CHAR(col, 'YYYY-MM-DD HH24:MI:SS')          -- timestamp
CASE WHEN col THEN 1 ELSE 0 END                -- boolean → NUMBER(1)

-- 적재(Oracle, SQL*Loader CTL): 동일 포맷 마스크로 역변환
load_dtm TIMESTAMP "YYYY-MM-DD HH24:MI:SS"
Result결과

timestamp 컬럼을 DATE로 정상 역변환하며 1,710,788건을 손실 없이 적재. 타입 체계 차이를 "아는 것"과 무손실 변환 로직을 "설계하는 것" 사이의 간극을 체감했고, 이 경험은 Oracle → MySQL 같은 이기종 전환에서 타입 매핑 오류를 사전에 예측하는 기준이 됩니다.

Oracle → PostgreSQL · ora2pg

ora2pg와 DBD::Oracle 간 Perl 런타임 불일치

Issue문제 발생

ora2pg를 표준 절차로 설치한 상태에서는 Oracle에 연결할 수 없었습니다. 또한 TYPE=COPY 모드는 데이터 파일만 생성하고 대상 테이블 DDL은 만들지 않았습니다.

Analysis분석

ora2pg 실행 파일의 셔뱅(#!/usr/bin/env perl)이 시스템 Perl 5.26.3을 호출하는데, DBD::Oracle 모듈은 Oracle 번들 Perl 5.38.2 경로에만 설치되어 있었습니다.

Solution해결
  • 셔뱅을 Oracle 번들 Perl 절대 경로로 교체하고, PERL5LIB=/usr/local/share/perl5로 Ora2Pg.pm 경로를 연결. 필요한 libnsl.so.1 심볼릭 링크를 확인·생성하고 perl -MDBD::Oracle로 로딩 검증.
  • 대상 DDL은 dba_tab_columns · dba_constraints · dba_indexes를 조회해 PostgreSQL 문법으로 자동 생성 (VARCHAR2 → varchar(N), NUMBER → numeric/integer/bigint, DATE → timestamp(0)).
  • REPLACE_TABLES / REPLACE_COLS로 대문자 식별자를 소문자로 치환, DATA_LIMIT 50000 · JOBS 4로 추출.
Result결과

APT_SALES 3,441,651건을 약 92초에 추출(약 656MB) → scp 전송 → psql 적재. 건수 일치와 함께 DBeaver에서 두 DB에 동일 조건 쿼리를 실행해 같은 32건이 반환됨을 교차 검증했습니다.

Oracle · Install

Oracle 19c 설치 프로그램이 인식하지 못하는 Rocky Linux 8

Issue문제 발생

Rocky Linux 8은 Oracle 19c OUI가 공식적으로 인식하는 배포판이 아니어서 CVU(Cluster Verification Utility)가 설치를 중단시킬 수 있었습니다.

Analysis분석

배포판 식별값을 우회하되, 이 설정이 영구히 남으면 이후 패치·점검 도구가 OS를 잘못 인식할 위험이 있다고 판단했습니다.

Solution해결

export CV_ASSUME_DISTID=OL7을 .bash_profile에 등록하지 않고 설치 시점 셸 레벨에서만 적용한 뒤 Silent 설치 진행. 이후 OPatch를 최신 버전으로 교체하고 opatch prereq CheckConflictAgainstOHWithDetail로 충돌 검사 후 RU 19.25를 적용했습니다.

Result결과

Oracle 19.25.0.0 EE 설치 및 패치 완료, opatch lspatches로 적용 확인. 우회 설정은 필요한 시점·범위로만 한정해 이후 패치·점검 도구에 영향을 남기지 않았습니다.

Tuning & 검증

성능과 안정성을 위해 적용한 설정, 그리고 설치·운영 검증

Oracle 파라미터 튜닝

약 70개 파라미터를 parameter_setting.sql로 관리. 적응형 옵티마이저 기능(optimizer_adaptive_plans, 동적 샘플링, bind peeking, feedback)을 비활성화해 Plan Stability와 부하 테스트 재현성을 확보하고, LGWR 관련 설정으로 로그 동기화 가변성을 줄였습니다.

PostgreSQL 메모리 · OS 설계

shared_buffers 4GB, effective_cache_size 12GB, work_mem 64MB, maintenance_work_mem 512MB. vm.overcommit_memory=2와 systemd OOMScoreAdjust=-1000으로 OOM Killer에 의한 DB 프로세스 종료를 차단했습니다.

HugePages · THP

두 DB 모두 THP를 GRUB 파라미터로 비활성화하고 표준 HugePages 적용. PostgreSQL은 4096MB ÷ 2MB = 2,048개 + 여유 10%로 2,300개를 산정하고 huge_pages=on으로 확보 실패를 즉시 드러나게 설정했습니다.

대용량 적재 최적화

데이터(TS_SDATA)와 인덱스(TS_SINDX) Tablespace 분리로 I/O 경합 완화. SQL*Loader Direct Path로 버퍼 캐시를 우회하고, PostgreSQL 일회성 벌크 로드에서는 synchronous_commit=off의 트레이드오프를 이해하고 적용했습니다.

Slow Query 추적 기반

pg_stat_statements(track=all, track_io_timing=on)와 log_min_duration_statement=1000으로 1초 초과 쿼리만 선별 로깅. Oracle은 ASH 기반 Top SQL·Wait Class·Blocking 세션을 Custom Metric으로 수집했습니다.

보안 · 운영 기본기

pg_hba.conf에 scram-sha-256 적용, Exporter DSN을 EnvironmentFile(640 권한)로 분리, 모니터링 전용 DB 계정에 최소 권한(필요 V$ 뷰 SELECT, pg_monitor)만 부여했습니다.
